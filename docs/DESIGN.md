# 架构决策与30分钟答辩提纲

## 核心判断

任务入口、理解、路由和执行环境不是同一个问题。我们选择“电脑运行规划器＋同一台实体手机执行”，而不是让云手机替代被测设备。最小闭环不追求任意 App：日历直接修改目标状态，只有明确要求进入页面才使用 GUI。上层模型只输出允许清单中的目标；具体权限、设备资格及是否可执行由确定规则检查，确认后才执行。

## 已实现分层

1. **理解**：固定规则语法或显式选择的 DeepSeek 规划，输出日程目标/固定设置目标或澄清问题。对日期、标题、时长、额外提醒/邀请需求做约束；不是自由工具规划器。
2. **路由与授权**：能力清单、设备实时状态、日历资格、目标 App 冲突、人工确认。不同意或任一目标不支持时停止，不偷偷丢弃需求。
3. **系统通道**：ADB shell 调用 Calendar Provider，写入前持久记账，按目标标记与字段回读。未知结果不盲目重试，已有事件不会自动删除。
4. **GUI 通道**：AutoGLM 使用原生副屏帧，只允许已限定的设置导航；scrcpy 服务端请求 OWN_FOCUS / STEAL_TOP_FOCUS_DISABLED 并读取实际标记。主屏仍是用户交互空间。
5. **验证与退出**：回读日历或目标 Activity/原生帧，记录主屏焦点/IME状态和人工观察，关闭自有副屏。完成信息目前只出现在电脑。

代码导航：`core/work/router/planner_client.py`（理解传输）、`planning.py`（目标/路由）、`calendar_tool.py`（写入/防重）、`gui_tool.py`（GUI桥接）、`core/work/focus_experiment/`（显示补丁）、`core/work/frame_stream/`（原生取帧）。

## 为什么没选其他方案

- 云手机/另一实体机可以隔离资源，但不能直接证明题目要求的同一台手机。
- 分屏/小窗仍占用用户主屏；普通后台进程或 Work Profile 也不自动解决输入焦点。
- 全部用 GUI 会为可以直接完成的日历写入引入更多界面状态；全部用 API 又覆盖不了没有接口的 App。
- 没有修改系统全局焦点开关、root、全局输入法或剪贴板。基线副屏能够导航，不代表所有 App、所有文字和音频都隔离。

## 失败怎样推动决策

- 虚拟显示创建及 Activity 切换曾造成主屏键盘白屏；改为每显示焦点相关标记并实机观察，不能只相信“标记设置成功”。
- Mac 窗口截取尺寸/可见性不可靠，改从同一副屏视频流取帧；动态抖音页面又暴露“本地新PNG不等于实时画面”的限制，尝试低帧率并保留未解决的时间戳对齐问题。
- 抖音播放视频泄漏声音，引入只针对抖音包的临时音频权限事务，退出恢复原值；明确不是通用副屏音频方案。
- 模型标签遗漏、复述示例和动作区域限制造成多次停止；固定数字内容交给受限执行器，模型不必再次生成 Type。最后一次可用证据来自助手看图导航，不冒充 AutoGLM 完整成功。
- 中文没有沿用成功的 ASCII 结论：实机字符映射预检失败即停，没有为赶工引入全局输入法/剪贴板替代。

## 如何与 Coding Agent 协作

人给出任务边界、手机观察和方向取舍；Coding Agent 搜索/阅读源码、实现小步适配、补离线测试、归档证据。输入和发送分别核对，未知结果停止；成功代码用独立工作树和标签保留，实验不覆盖旧基线。测试使用假 SDK/设备/Provider，不把离线绿灯代替真机观察。应能现场解释本次提交中的关键保护与局限，而不是只展示模型生成的代码量。

## 建议答辩时间

5分钟问题与取舍；5分钟主线演示；8分钟显示/输入/取帧和确定性路由；7分钟失败复盘与AI协作；5分钟边界和后续工作。后续可扩展事件入口、异步确认、多应用能力注册和真正的 Unicode 输入适配，但这些均未计入本次已实现功能。
